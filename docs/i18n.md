# Localization

Prelude includes English (`en`) and Spanish (`es`) using **next-intl 4.14.8** for Next.js and **use-intl 4.14.8** for the standalone MCP App. The browser-safe `@repo/i18n` package owns supported locales, selection helpers, and shared JSON catalogs. No translation service, account, environment variable, or generation command is required.

## Choose a language

Start with `pnpm dev` or either Docker stack. On the first visit, the website selects a supported language from the browser's `Accept-Language` preferences, with English as the fallback. Regional preferences such as `es-MX` resolve to Spanish. Use the header's **Language / Idioma** selector to override that preference.

The selector saves a `PRELUDE_LOCALE` cookie for one year, scoped to `/` with `SameSite=Lax`. Only supported values are trusted; invalid saved values are ignored. The saved choice takes precedence on later requests. Cookie scope follows the hostname/path rather than the port, so `localhost` and `127.0.0.1` can have different choices while ports on the same hostname share it. Other tabs on the same hostname see the saved preference on their next server request; changing it does not broadcast a UI language change. Clear this cookie to test first-visit detection again.

Public URLs stay unchanged: `/`, `/playground`, and `/playground?status=active#tasks` work in either language. Switching language validates and saves the cookie through a Server Action, invalidates pre-switch Router Cache entries, and refreshes the current route while retaining its pathname, search parameters, hash, history, and scroll position. The selector becomes usable after hydration so its change cannot be lost before React attaches the handler. API paths and query values such as `all`, `active`, and `completed` remain stable.

The selector uses React's [`useSyncExternalStore` server snapshot contract](https://react.dev/reference/react/useSyncExternalStore#adding-support-for-server-rendering) for this one-time readiness check: the server/initial hydration snapshot is `false`, and the client snapshot is `true`. There is no external event stream to subscribe to, so the stable subscription returns an empty cleanup. This avoids initializing state in a mount-only effect, which the pinned React Doctor warns against. Removing the guard can lose a selection made before hydration; replacing the cookie action with a prefixed locale navigation can lose the URL fragment or restore stale filter history.

Language selection does not translate user task titles. Task data, API schemas and descriptions, tool names, operation IDs, JSON arguments/results, and the third-party Scalar and Inspector interfaces stay English or retain their original content. Developer documentation remains English.

## Package and route boundaries

| Location | Responsibility |
| --- | --- |
| `packages/i18n/src/index.ts` | Supported locales, default locale, cookie constants, and browser/request preference helpers. |
| `packages/i18n/src/messages/{en,es}` | `site.json`, `tasks.json`, `mcp.json`, `pwa.json`, and `widget.json` catalogs. |
| `@repo/i18n/messages` | Complete website catalogs and their shared message type. |
| `@repo/i18n/pwa` | Only PWA messages for the static offline document. |
| `@repo/i18n/widget` | Only widget messages for the standalone MCP App bundle. |
| `apps/web/src/i18n/routing.ts` | next-intl routing, cookie policy, and `localePrefix: "never"`. |
| `apps/web/src/proxy.ts` | Language negotiation and an internal rewrite to the locale route. |
| `apps/web/src/i18n/request.ts` | Validated locale and messages from `next/root-params`. |
| `apps/web/src/i18n/navigation.ts` | Locale-aware `Link`, router, pathname, and redirect helpers. |
| `apps/web/src/i18n/http-locale.ts` | Request cookie/header resolution for non-page routes such as the manifest. |
| `apps/web/src/app/actions/locale.ts` | Validated preference cookie writes and Router Cache invalidation. |
| `apps/web/src/app/[locale]` | Localized root layout, homepage, playground, loading, error, and not-found UI. |
| `apps/web/src/app/(standalone)/offline` | A separate static offline page that needs no request-specific server rendering. |

The internal `[locale]` segment gives Next.js a distinct route value for each language while next-intl keeps that segment out of public URLs. `generateStaticParams()` lists both supported languages. The root layout sets `<html lang>` and localized metadata, then passes only client-used namespaces to `NextIntlClientProvider`. Server-only homepage and playground copy does not need to be serialized into that provider.

The proxy excludes `/api/`, `/offline`, Next.js assets, and file paths containing a dot. The API and static offline document therefore keep their existing route boundaries. Language-specific SEO alternate links are disabled because both languages share the same public URLs. The proxy delegates rewrites and redirects directly to next-intl, without repairing their URL headers. `skipProxyUrlNormalize` preserves the original server URL to avoid [Next.js's loopback-origin normalization issue](https://github.com/vercel/next.js/issues/94745) in the pinned 16.3.6 release. next-intl builds same-origin rewrites from that URL, and Next.js converts same-origin prefix-removal redirects into relative browser locations. This preserves the public host/port behind Docker without an outbound self-proxy or leaking the internal listening address. Recheck this workaround after a framework upgrade. A reverse proxy should preserve the original Host and protocol, as required by the application's existing Server Action and origin checks.

Unknown page routes show a localized not-found boundary with `noindex`, using [next-intl's documented catchall pattern](https://next-intl.dev/docs/environments/error-files#catching-unknown-routes). Next.js can return HTTP 200 when that boundary is streamed; API error status codes remain unchanged. The catchall immediately calls `notFound()` and has no page shell, so it uses the documented, narrowly scoped [`instant = false` opt-out](https://nextjs.org/docs/app/api-reference/file-conventions/route-segment-config/instant#disabling-static-shell-validation). The pinned validator exempts framework-generated error routes, but treats this custom catchall as an ordinary page. All real pages retain validation; no global opt-out or artificial loading shell is added.

## Add and use messages

Add each key to both language catalogs. Website namespaces are `Common`, `Home`, `Playground`, `Animation`, `Errors`, `Tasks`, `Mcp`, and `Pwa`; the standalone widget uses `Widget`. `Messages` derives from the English catalogs, the Spanish catalog must match that shape, and catalog tests check aligned keys.

Use `getTranslations` in Server Components:

```tsx
import { getTranslations } from "next-intl/server";

export async function SectionHeading() {
  const t = await getTranslations("Playground");
  return <h2>{t("workbenchHeading")}</h2>;
}
```

Use `useTranslations` in website Client Components and import the same hook from `use-intl` inside the MCP App:

```tsx
const t = useTranslations("Tasks");
return <span>{t("count", { count: tasks.length })}</span>;
```

ICU messages handle counts and interpolation; do not build translated sentences by concatenating fragments. For example, the task-count message uses `one` and `other` plural branches. Use rich-text messages with explicit React callbacks for inline links/code, following the playground's widget description. User content remains a value passed to the message and is rendered as text.

Use the locale-aware helpers from `@/i18n/navigation` for website navigation. API/documentation links keep their stable `/api/` addresses. Keep errors as typed codes in state or action responses, then translate them during rendering. This lets an existing validation or connection error change language without replacing a draft or repeating the request. Raw protocol results displayed by the JSON tool explorer remain faithful to the server response.

English is the unsupported-language fallback, not a substitute for incomplete supported catalogs. Add all required keys and test their ICU formatting before exposing another locale. Missing translation keys should be fixed rather than hidden.

The website and widget configure a deterministic `UTC` translation time zone. Language and time zone are separate preferences; introduce an explicit validated time-zone policy if a product needs local date/time formatting. Use next-intl/use-intl formatters for locale-aware presentation and keep Temporal data/serialization rules from [the Temporal guide](temporal.md).

## Cache and request isolation

Locale comes from validated root parameters in page rendering, including cached components. The cached public stack overview can therefore render per-language content without reading cookies or headers inside `use cache`. Resolve request identity and other request-specific values outside cached scopes as before.

Public page URLs vary by language preference, so the proxy marks their responses `Cache-Control: private, no-store`. The manifest also sends `private, no-store` and varies on `Cookie, Accept-Language`. Preserve this policy when configuring a reverse proxy or CDN; a shared URL must not serve one visitor's language choice to another. Next.js's internal component caching remains separate from shared HTTP response caching.

Server QueryClients remain scoped to one request, while browser and widget QueryClients retain their existing instance lifetimes. Task query keys use stable protocol status values rather than translated labels. Next.js retains locale route trees separately with Activity, so website drafts, validation codes, density, and synchronous request guards live in browser-only Zustand stores shared across those trees. Server rendering always creates fresh stores; there is no local storage or cross-tab draft sharing. These in-memory drafts survive language changes and client navigation within the current document, then reset on a full reload. The language cookie persists independently. TanStack Query continues to own server data and tool execution results. Switching language preserves these values and public filter history.

Route Handlers and Server Actions do not inherit page root parameters. Use `getRequestLocale()` outside cached scopes where request-derived presentation is needed, or accept and validate an explicit locale. The current task APIs return their normal English public errors; website and widget presentation maps failures to translated codes instead of localizing business/protocol output.

## PWA and offline behavior

The manifest localizes its `description` and `lang` from the saved cookie/browser header. Its brand name, ID, start URL, scope, and icon URLs remain the same, so changing language does not create a separate PWA identity. Browsers control when an already installed app refreshes its manifest metadata.

Service-worker update toasts, actions, close labels, and notification-region labels use the current website language. One tab-scoped session owns the controller across locale route trees, and the active toast retains the same notification ID. Hidden Activity trees can retain hidden DOM; only the active notification is presented. Changing language does not re-register the worker, reset dismissal or the activation timeout, or grant activation/reload approval. The session releases its listeners and timers when the document is destroyed and survives a browser back/forward-cache pause.

Serwist still precaches one static `/offline` document. It initially renders readable English, including when JavaScript is disabled. After hydration, it selects the valid saved cookie, then browser language, then English, and updates the document language/title. Its PWA-only catalogs are bundled locally, so it needs no translation network request. There can be a brief English display before that client selection.

Successful HTML pages, RSC, APIs, docs, MCP resources, external URLs, and the preference-dependent manifest remain outside service-worker runtime caching. Localization adds no offline task store or queued writes.

## MCP App language

The widget selects a supported host-context locale first, browser language second, and English last. It uses its own `use-intl` provider and bundled `Widget` catalogs; it does not read the website's language cookie or import Next.js providers. A compatible host controls the widget's host context, so the website and an Inspector preview can show different languages.

`hostcontextchanged` notifications update the widget language, `<html lang>`, and document title. Partial context changes without a `locale` field retain the previous host preference. The update does not reconnect to MCP, discard an edit/new-task draft, reset the filter/query cache, or refetch initial tool results. Listener cleanup follows the widget connection lifecycle. Unsupported or malformed host locales fall back to supported browser preferences.

Both translations are part of the self-contained HTML resource, preserving the widget's no-external-assets CSP. Editing shared catalogs rebuilds the widget in native and Compose development. Close and reopen an Inspector App preview to load rebuilt HTML; an already open iframe retains its original bundle. Production translations require a build and deployment/restart, like other compiled source. Turbo restores the generated resource and service worker together.

## Add a locale or remove the demo

1. Add the locale to `locales` and `isLocale` in `packages/i18n/src/index.ts`; choose the desired `defaultLocale`.
2. Create complete catalog files under a new `messages/<locale>` directory and include them in the website, PWA, and widget catalog loaders. Keep their shapes and ICU arguments aligned with English.
3. Add a self-named option, with its `lang` attribute, to `language-selector.tsx`. Review document direction, manifest direction, layouts, fonts, and plural rules if adding a right-to-left language.
4. Update locale-selection, catalog-parity, component, and browser scenarios. Verify first-visit detection, cookie overrides, stable URLs/history, localized metadata, PWA fallback/toasts, widget host-context changes, and cache isolation.
5. Run frozen installation and `pnpm verify`; use `pnpm test:stack` to verify standalone packaging and Compose behavior when Docker's Linux engine is running.

When removing the task demo, update `apps/web/src/app/[locale]/playground/page.tsx`, the workbench/explorer/widget components, and their catalogs together. Remove obsolete `Tasks`, `Mcp`, and `Widget` keys and imports only after their consumers are gone; remove the corresponding namespaces from the client provider. Keep `Common`, `Errors`, `Pwa`, and the language infrastructure if the replacement product still needs localization. Follow [architecture](architecture.md#replace-or-remove-the-demo), [MCP removal](mcp.md#add-change-or-remove-tools), and [the MCP App checklist](mcp-apps.md#replace-or-remove-the-example) for transport/build boundaries.
