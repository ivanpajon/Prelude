# Localization

Prelude includes English (`en`) and Spanish (`es`) using **next-intl 4.14.8** for Next.js and **use-intl 4.14.8** for the standalone MCP App. The browser-safe `@repo/i18n` package owns supported locales, selection helpers, and shared JSON catalogs. No translation service, account, environment variable, or generation command is required.

## Choose a language and URL policy

Start with `pnpm dev` or either Docker stack. Prelude defaults to explicit language URLs: `/en`, `/es`, `/en/playground`, and `/es/playground`. Opening an unprefixed entry such as `/` negotiates a supported language from the saved preference, then the browser's `Accept-Language`, with English fallback. Regional preferences such as `es-MX` resolve to Spanish. With the demo enabled, an explicit supported language prefix always wins over saved preferences.

The header's **Language / Idioma** selector saves `PRELUDE_LOCALE` for one year. The **Language in URL / Idioma en la URL** switch in the homepage stack card changes actual URLs for the current visitor. Turn it off to browse `/` and `/playground` in the selected language; turn it on to restore that language's prefix. A separate `PRELUDE_LOCALE_ROUTING` session cookie stores the override. Selecting the project default removes the override; invalid values fall back to configuration. Explicit language links remain authoritative, even after choosing hidden URLs.

Both cookies use `Path=/` and `SameSite=Lax`. Cookie scope follows the hostname/path rather than the port: `localhost` and `127.0.0.1` can differ, while ports on one hostname share preferences. Other tabs observe saved preferences on later requests; there is no cross-tab UI broadcast. Canonical prefixed GET requests do not update preference cookies, so opening a shared language link does not silently overwrite a saved choice.

Controls validate and save both preferences before replacing the current history entry without a full document reload. Pathname, query parameters, fragment, scroll, and drafts survive. Prefixed language changes navigate to the corresponding language URL; unprefixed language changes save the cookie and refresh. Browser back/forward honors the language encoded in historical explicit URLs. Pending guards prevent overlapping preference writes, and errors remain retryable. API paths and query values such as `all`, `active`, and `completed` remain stable.

The hydration readiness guard uses React's [`useSyncExternalStore` server snapshot contract](https://react.dev/reference/react/useSyncExternalStore#adding-support-for-server-rendering): server/initial hydration returns `false`, client returns `true`, and the stable subscription has no event stream. This prevents an early interaction being lost before handlers attach. It does not determine routing, repair server-rendered links, or read browser cookies: the server already renders the correct language and mode.

Edit the static `routingSettings` in `apps/web/src/i18n/routing.ts` to choose a product policy:

| Setting | Default | Effect |
| --- | --- | --- |
| `defaultMode` | `"always"` | Explicit language URLs. Use `"never"` for one public URL per page. |
| `demoEnabled` | `true` | Show the card switch and accept visitor overrides. Set `false` to hide it and enforce the configured policy. |

These are source/build settings, not runtime environment variables. With the demo disabled, stale mode cookies are ignored. Both fixed policies use the same routing and translation implementation.

Language selection does not translate user task titles. Task data, API schemas and descriptions, tool names, operation IDs, JSON arguments/results, and the third-party Scalar and Inspector interfaces stay English or retain their original content. Developer documentation remains English.

## Package and route boundaries

| Location | Responsibility |
| --- | --- |
| `packages/i18n/src/index.ts` | Supported locales, default locale, cookie constants, and browser/request preference helpers. |
| `packages/i18n/src/messages/{en,es}` | `site.json`, `tasks.json`, `mcp.json`, `pwa.json`, and `widget.json` catalogs. |
| `@repo/i18n/messages` | Complete website catalogs and their shared message type. |
| `@repo/i18n/pwa` | Only PWA messages for the static offline document. |
| `@repo/i18n/widget` | Only widget messages for the standalone MCP App bundle. |
| `apps/web/src/i18n/routing.ts` | Static policy settings and both next-intl routing configurations. |
| `apps/web/src/proxy.ts` | Language negotiation and an internal rewrite to the locale route. |
| `apps/web/src/i18n/request.ts` | Validated locale and messages from `next/root-params`. |
| `apps/web/src/i18n/navigation.tsx` | Mode-aware client `Link`, router, and pathname helpers. |
| `apps/web/src/i18n/server-navigation.ts` | Server navigation helpers with explicit validated routing mode. |
| `apps/web/src/i18n/http-locale.ts` | Request cookie/header resolution for non-page routes such as the manifest. |
| `apps/web/src/app/actions/locale.ts` | Validated preference cookie writes and Router Cache invalidation. |
| `apps/web/src/app/[routingMode]/[locale]` | Localized root layout, homepage, playground, loading, error, and not-found UI. |
| `apps/web/src/app/(standalone)/offline` | A separate static offline page that needs no request-specific server rendering. |

The internal `[routingMode]/[locale]` segments give Next.js four distinct variants (two policies × two languages), while public URLs contain at most a language prefix. `generateStaticParams()` lists all four combinations. Validated root parameters drive `<html lang>`, translations, metadata, and the mode-aware navigation provider, including inside cached components. The document reads no cookies or headers and needs no document-level Suspense boundary or validation exemption. Only client-used namespaces are serialized into `NextIntlClientProvider`.

The proxy selects a configured next-intl handler, then composes an internal mode rewrite while preserving its headers, cookies, and request overrides. Internal mode segments are not public entrypoints. It excludes `/api/`, `/offline`, Next.js assets, and file paths containing a dot. `skipProxyUrlNormalize` preserves the raw origin to avoid [Next.js's loopback-origin normalization issue](https://github.com/vercel/next.js/issues/94745) in the pinned 16.3.6 release. No manual Host/protocol repair is added. Recheck the workaround after upgrades; a reverse proxy must preserve the original Host and protocol for Server Actions and origin checks.

Unknown page routes show a localized not-found boundary with `noindex`, using [next-intl's documented catchall pattern](https://next-intl.dev/docs/environments/error-files#catching-unknown-routes). Next.js can return HTTP 200 when that boundary is streamed; API error status codes remain unchanged. The catchall immediately calls `notFound()` and has no page shell, so it uses the documented, narrowly scoped [`instant = false` opt-out](https://nextjs.org/docs/app/api-reference/file-conventions/route-segment-config/instant#disabling-static-shell-validation). The pinned validator exempts framework-generated error routes, but treats this custom catchall as an ordinary page. All real pages retain validation; no global opt-out or artificial loading shell is added.

## Add and use messages

Add each key to both language catalogs. Website namespaces are `Common`, `Home`, `Playground`, `Animation`, `Errors`, `Tasks`, `Mcp`, and `Pwa`; the standalone widget uses `Widget`. `Messages` derives from the English catalogs, the Spanish catalog must match that shape, and catalog tests check aligned keys.

Use `getTranslations` in Server Components:

```tsx
import { getTranslations } from "next-intl/server";

export async function SectionHeading() {
  const t = await getTranslations("Playground");
  return <h2>{t("workbenchHeading")}</h2>;
}
```

Use `useTranslations` in website Client Components and import the same hook from `use-intl` inside the MCP App:

```tsx
const t = useTranslations("Tasks");
return <span>{t("count", { count: tasks.length })}</span>;
```

ICU messages handle counts and interpolation; do not build translated sentences by concatenating fragments. For example, the task-count message uses `one` and `other` plural branches. Use rich-text messages with explicit React callbacks for inline links/code, following the playground's widget description. User content remains a value passed to the message and is rendered as text.

Use mode-aware `Link` and client hooks from `@/i18n/navigation` for website navigation. Server pathname/redirect helpers live in `@/i18n/server-navigation` and take an explicit routing mode; obtain it from validated root parameters in page rendering. API/documentation links keep their stable `/api/` addresses. Keep errors as typed codes in state or action responses, then translate them during rendering. This lets an existing validation or connection error change language without replacing a draft or repeating the request. Raw protocol results displayed by the JSON tool explorer remain faithful to the server response.

Server navigation helpers do not save preferences. Use the current validated locale for ordinary redirects. In unprefixed mode, passing a different locale cannot select that language through the URL; language changes must save the preference first through the shared control/action.

English is the unsupported-language fallback, not a substitute for incomplete supported catalogs. Add all required keys and test their ICU formatting before exposing another locale. Missing translation keys should be fixed rather than hidden.

The website and widget configure a deterministic `UTC` translation time zone. Language and time zone are separate preferences; introduce an explicit validated time-zone policy if a product needs local date/time formatting. Use next-intl/use-intl formatters for locale-aware presentation and keep Temporal data/serialization rules from [the Temporal guide](temporal.md).

## Cache and request isolation

Locale comes from validated root parameters in page rendering, including cached components. The cached public stack overview can therefore render per-language content without reading cookies or headers inside `use cache`. Resolve request identity and other request-specific values outside cached scopes as before.

Explicit language URLs are deterministic, emit language alternate links, and retain Next.js's normal response caching behavior. Negotiated redirects and unprefixed pages depend on visitor preferences, so they are `private, no-store`; the manifest also varies on `Cookie, Accept-Language`. Hidden-URL demo overrides send `X-Robots-Tag: noindex` and omit alternate links. A configured fixed unprefixed product does not inherit the demo's noindex override, but cannot distinguish translated pages with URL-based language alternates. Next.js component caching remains separate from shared HTTP caching.

For blogs and public sites, retain explicit language URLs, add a deployment-specific `metadataBase`, and emit canonical and sitemap entries for actual public URLs. Keep canonical URLs consistent with translations and content availability; do not expose internal mode segments. Prelude does not invent a deployment origin. For dashboards, place request-dependent identity/data behind local Suspense boundaries and keep private data outside public caches. Locale routing does not replace authentication or authorization. Static content here means prerendered pages in the server-capable stack; full static export requires a separate deployment adaptation.

Server QueryClients remain scoped to one request, while browser and widget QueryClients retain their existing instance lifetimes. Task query keys use stable protocol status values rather than translated labels. Next.js retains locale and routing-mode trees separately with Activity, so website drafts, validation codes, density, and synchronous request guards live in browser-only Zustand stores shared across those trees. Server rendering always creates fresh stores; there is no local storage or cross-tab draft sharing. These in-memory drafts survive language changes and client navigation within the current document, then reset on a full reload. The language cookie persists independently. TanStack Query continues to own server data and tool execution results. Switching language or URL policy preserves these values and filter history.

Route Handlers and Server Actions do not inherit page root parameters. Use `getRequestLocale()` outside cached scopes where request-derived presentation is needed, or accept and validate an explicit locale. The current task APIs return their normal English public errors; website and widget presentation maps failures to translated codes instead of localizing business/protocol output.

## PWA and offline behavior

The manifest localizes its `description` and `lang` from the saved cookie/browser header. Its brand name, ID, start URL, scope, and icon URLs remain the same, so changing language does not create a separate PWA identity. Browsers control when an already installed app refreshes its manifest metadata.

Service-worker update toasts, actions, close labels, and notification-region labels use the current website language. One tab-scoped session owns the controller across locale route trees, and the active toast retains the same notification ID. Hidden Activity trees can retain hidden DOM; only the active notification is presented. Changing language does not re-register the worker, reset dismissal or the activation timeout, or grant activation/reload approval. The session releases its listeners and timers when the document is destroyed and survives a browser back/forward-cache pause.

Serwist still precaches one static `/offline` document. It initially renders readable English, including when JavaScript is disabled. After hydration, it selects the valid saved cookie, then browser language, then English, and updates the document language/title. Its PWA-only catalogs are bundled locally, so it needs no translation network request. There can be a brief English display before that client selection.

Successful HTML pages, RSC, APIs, docs, MCP resources, external URLs, and the preference-dependent manifest remain outside service-worker runtime caching. Localization adds no offline task store or queued writes.

## MCP App language

The widget selects a supported host-context locale first, browser language second, and English last. It uses its own `use-intl` provider and bundled `Widget` catalogs; it does not read the website's language cookie or import Next.js providers. A compatible host controls the widget's host context, so the website and an Inspector preview can show different languages.

`hostcontextchanged` notifications update the widget language, `<html lang>`, and document title. Partial context changes without a `locale` field retain the previous host preference. The update does not reconnect to MCP, discard an edit/new-task draft, reset the filter/query cache, or refetch initial tool results. Listener cleanup follows the widget connection lifecycle. Unsupported or malformed host locales fall back to supported browser preferences.

Both translations are part of the self-contained HTML resource, preserving the widget's no-external-assets CSP. Editing shared catalogs rebuilds the widget in native and Compose development. Close and reopen an Inspector App preview to load rebuilt HTML; an already open iframe retains its original bundle. Production translations require a build and deployment/restart, like other compiled source. Turbo restores the generated resource and service worker together.

## Add a locale or remove the demo

1. Add the locale to `locales` and `isLocale` in `packages/i18n/src/index.ts`; choose the desired `defaultLocale`.
2. Create complete catalog files under a new `messages/<locale>` directory and include them in the website, PWA, and widget catalog loaders. Keep their shapes and ICU arguments aligned with English.
3. Add a self-named option, with its `lang` attribute, to `language-selector.tsx`. Review document direction, manifest direction, layouts, fonts, and plural rules if adding a right-to-left language.
4. Update locale-selection, catalog-parity, component, and browser scenarios. Verify first-visit detection, cookie overrides, both URL policies/history, localized metadata, PWA fallback/toasts, widget host-context changes, and cache isolation.
5. Run frozen installation and `pnpm verify`; use `pnpm test:stack` to verify standalone packaging and Compose behavior when Docker's Linux engine is running.

When removing the task demo, update `apps/web/src/app/[routingMode]/[locale]/playground/page.tsx`, the workbench/explorer/widget components, and their catalogs together. Remove obsolete `Tasks`, `Mcp`, and `Widget` keys and imports only after their consumers are gone; remove the corresponding namespaces from the client provider. Keep `Common`, `Errors`, `Pwa`, and the language infrastructure if the replacement product still needs localization. Follow [architecture](architecture.md#replace-or-remove-the-demo), [MCP removal](mcp.md#add-change-or-remove-tools), and [the MCP App checklist](mcp-apps.md#replace-or-remove-the-example) for transport/build boundaries.
